## What the pass changes

Today the queue reads three kinds of item: a design, a triage list, and a packet. `approval-queue report` prints the usage text (mechanism 1), and the app leaves an item of any other kind unlisted and unserved (mechanism 2).

After this pass a conductor runs `approval-queue report <initiative> <round> <report.md>`. The command stores the file as an item of a fourth kind, `report`, prints the item's id, and exits without waiting. The board shows the report as the first row of its round, labelled "Round report". Its page shows the report's Markdown, the round's waiting packets and landed pull requests as links, and one button, "Mark read". The button moves the report to history. A second `report` for a round whose report still waits replaces it.

A report is never merged, collected, or logged. It records no process id, so no page calls it abandoned.

Out of scope: a key for "Mark read", a hold or an Undo on it, the round or the repo in the report's own board heading, a size limit on the report file, the round on the history page's rows, a refusal worded for a report in `reply` (backlog, task 3), and backlog items #38, #41, #49, #64, #65, and #66. The live server is never rebuilt or restarted in this pass, and the executor never runs the installed `approval-queue`. The command reaches the live queue when the main checkout pulls, because `~/.local/bin/approval-queue` points there (mechanism 30). The pages reach it when the conductor runs `approval-queue restart` after the PR lands. A report queued before that restart doesn't show (mechanism 2, and the build design's line 407).

## Planner's calls

The build design leaves "the report page's route, and each page's markup" to the builder. These calls fill that in.

- The report opens at `/item/<id>`, the route every item uses. The rail, the board, the history page, and `restart`'s page check already link there (mechanism 32). A second route would need each of them to branch.
- The command stores the title and nothing else it could compute. The board's headline ("3 of 4 passes merged, 1 parked") is computed in the app from `report.md`, by a pure function. A wrong headline is then fixed by a restart, with no report to queue again.
- The headline reads the first table whose header row has a `State` cell. It gives "<merged> of <rows> passes merged", then ", <n> <state>" for each other state in the order the table first shows it. A report with no such table shows its title as the headline.
- The title is the text of the file's first line when that line starts with `# `. Otherwise it is "Round <round>".
- `report` takes the initiative `packet` takes: `none`, or the id of a record under `APPROVAL_QUEUE_PROJECTS` (mechanism 11). One check serves both commands.
- A file the command can't read exits 1 with "cannot read", as `reply` does (the command's line 288). A file with no non-blank line exits 2: replacing a waiting report with an empty one would throw away what Geoff has not read yet. The report has no size limit. It is one page of text a conductor writes.
- "Replaces" means the command retires every waiting report of the same initiative and round with `retire_item` (mechanism 9), under `queue.lock` (mechanism 10), and then writes the new item under a new id. The old directory keeps its `report.md` and loses its `item.json`, as a withdrawn packet does. A report Geoff has already read is decided, so it stays in history and the new one queues beside it.
- If Geoff presses "Mark read" while the command retires that report, `retire_item` sees the decision, puts `item.json` back, and returns 1 (mechanism 9). The read report goes to history, and the new one queues. The command runs under `set -euo pipefail` (its line 4), so it calls `retire_item` in a form that can't end the script on that 1.
- One window stays open, a few milliseconds wide, and no test covers it. The app writes `decision.json`, finds no `item.json`, and takes its decision back (mechanism 21) in the instant the command sees that decision and puts `item.json` back. The old report then waits beside the new one. After a 1, the command looks for `decision.json` again and retires the report once more when it is gone, which narrows the window. The next `report` for the round closes it, because the command retires every match.
- `report` starts no server and opens no tab. The conductor runs it unattended, and the queue's open tab polls the rail.
- `merge` and `collect` name a report before any other refusal that could fire on it. Today `merge` says "has no pull requests to merge" and `collect` says "is a report item, which this queue no longer reads" (mechanisms 5 and 6). Both would mislead a session.
- `withdraw` on a report gets a refusal of its own, as an added check. Today a waiting report gets "was queued before withdraw existed; stop its command" (mechanism 7), and a read one gets "is decided; collect it instead" (the command's line 61). A report has no command to stop, and `collect` refuses it. The new words say that a report isn't withdrawn and that the next `report` for its round replaces it.
- `pending`'s kind list doesn't change. A report has no `pid`, so the loop skips it one line before the kind list (mechanism 8). The comment above `pending` gains the report, and a test holds the behavior.
- On the board the report keeps `single`, set to "Round report", so the row shows that label where a packet shows its rules, and a dash where a packet shows its asks (mechanism 15). The row carries its `round` and its initiative's group, so it sits in its round's section. The section's rows keep the chosen order, and the report is then moved to the front. Sections and groups are ranked before that move, so a new report never reorders the board.
- A round that holds only a report gets the heading "Round <id>" with no repo name. The command takes no repo, and the heading's names come from packet rows (mechanism 17).
- The app still opens on the oldest waiting packet. A report is a single, and `openingRow` skips singles (mechanism 16).
- In the rail the report is the first entry of its round. Its text is the headline, and the line under it reads "Round report, 5 minutes ago".

The waiting list links each waiting packet of the same initiative and round to `/item/<id>`. The landed list links each digest line of that round to its pull request on GitHub, with the claim beside it. Each list has one sentence for when it is empty.
