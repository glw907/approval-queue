## What the pass changes

Geoff can select a passage on a document and write a note on it. The note is stored as a thread, sits beside its passage in the margin (or in a sheet on a narrow screen), and survives a reload. A waiting session reads the threads with `notes <id>`, answers one with `reply`, or starts its own, which the page labels "Claude". When the session sends a fixed version back with `send --returns <id>`, the page marks what changed since the version Geoff read, a switch hides the marks, and a thread whose passage changed shows the original words above the new ones. Send back is refused when Geoff has written no note and changed no answer, since the session would have nothing to act on. Nothing Geoff uses changes: the live queue on port 7907 stays the old app until A6.

## Planner's calls

1. **Three files outside the design's list.** `next/src/lib/strings.ts` holds every page string, as A3 and A4 used it (A4 call 1). `next/src/lib/store/store.ts` gains one generic numbered-record append, generalized from `writeDecision` (mechanism 1), so notes are written race-free (call 2), plus its test in `store.test.ts`. `writeDecision` becomes a call of the new function with the `decision` prefix, and its tests keep passing unchanged. `checkName` also refuses `note-` names. All three go into `## Decisions`, and `## Planning misses` carries one design-stage `[file-list]` line naming them.
2. **A note is a record, never a rewritten file.** The page and a session's `reply` can write at the same moment, so a thread store that is read, changed, and written back can lose one of them. Each note operation is a `note-<n>.json` record in the document's directory, numbered and linked like a decision (mechanism 1), never replaced. The operations:
   - `{ op: 'open', who, quote, start?, version, text, at }` starts a thread; its id is the record's `n`.
   - `{ op: 'reply', thread, who, text, at }` adds an entry.
   - `{ op: 'resolve', thread, resolved, who, at }` folds a thread shut or opens it again.
   - `{ op: 'delete', thread, at }` removes a thread whose every entry is Geoff's, as the mockup allows (mechanism 9).

   `who` is `geoff` or `claude`. `version` is the document version the quote was taken from. `PageDoc` gains `version`, the page posts it with each `note`, and the server stores it when it is at most the newest stored version, else refuses with 400; a page left open across a return therefore keeps its quote's true version. A session's `reply` stores the newest stored version. A `note-<n>.json` that doesn't parse, or lacks its operation's fields, is skipped by the fold and listed in its `bad` field; `notes` prints each one on stderr and still exits 0, and the page still loads, so a bad note never blocks a decision. A new `next/src/lib/components/notes.server.ts` folds the records, in number order, into `Thread { id, quote, start?, was?, orphan?, resolved, entries: { who, text, at }[] }`, and drops a deleted thread and any record naming an unknown thread. A thread id appears in the `notes` JSON and in the page's posts, never as text on a page.
3. **A passage that changed keeps its original words.** `was` is derived on read, never stored. For a thread whose `version` is older than the newest, the fold runs `compare(v<version>, v<newest>)` (mechanism 3) and looks for the thread's quote inside the plain text of a passage's removed words, `plain(curly(renderInline(removed)))`, with both sides normalized as call 4 says: the removed words' plain text reads a straight `#233's` where Geoff's quote from the page reads `#233’s`. When it finds one, `was` is the original quote and the thread's quote becomes the plain text of that passage's added words, with no `start`. When the passage has no added words, the thread is an orphan, which the mockup draws with `NOTES.orphan` (mechanism 9). A quote found in no changed passage keeps its quote and drops its `start`, since offsets shift between versions. A quote that straddles a passage's edge, found whole in neither the removed words nor the unchanged text, keeps its quote and is an orphan. A `whole` comparison makes every older thread an orphan with its quote kept.
4. **The page anchors by text, the server by quote.** The page builds its text index from the article's text nodes, skipping any node inside `del` or `[data-no-notes]`, as the mockup's `Annotated` does (mechanism 6). The question's `sr-only` `<legend>` (`Document.svelte:313`) gains `data-no-notes`, so no thread anchors on text the reader can't see. Offsets are therefore the same with marks drawn or hidden. A thread anchors at the occurrence of its quote that starts nearest its `start`, or at the first occurrence when it has none. Matching normalizes both sides: curly quotes to straight, and each run of white space to one space, because `curly()` turns a session's straight `can't` into the page's `can’t` (mechanism 5). A quote the page can't find on the newest version draws as an orphan card. The highlight is drawn with the CSS Custom Highlight API, as the mockup does (mechanism 8).
5. **`notes <id>`.** A new `next/cli/notes.ts` prints `{ id, threads }` as JSON on stdout, the fold of call 2 with call 3's `was`, and exits 0. An unknown id exits 1 with the store's message. It imports the fold from `notes.server.ts`, so the command and the page read one fold.
6. **`reply`.** `reply <id> <thread> <text.md>` adds a `claude` entry to that thread. `reply <id> <text.md>`, with no thread, starts one: the file opens with a Markdown blockquote holding the quoted passage, and the rest is the note. A session copies the blockquote from its `.md`, which carries Markdown such as `` `round.md` `` (`content/20-survey-edit.md:24`), so `reply` strips the `> ` prefixes, joins the lines with a space, and stores `plain(curly(renderInline(quote)))` (`render.ts:47` and `:65`), the text the page draws. The new thread is signed `claude`, with its `version` the newest stored and no `start`, so a session may quote words of the version it is about to send with `--returns` and the page anchors it on read. Refused with exit 1 and a sentence on stderr: an unknown id or thread, a deleted or resolved thread, a withdrawn document, a missing or unreadable `text.md`, a file with no blockquote when no thread is named, an empty note, and a note over 4,000 characters, the count in the sentence (the failure table). The count is the note's code points, `[...text].length`, on the page, the server, and the command alike, so the three sentences agree. `main.ts` takes 2 or 3 arguments for `reply`; the `USAGE` line names `notes <id>`, `reply <id> [thread] <text.md>`, and `send --returns <id> <doc.md>`, keeping the prefix `usage: approval-queue check|send <doc.md>` that `check.test.ts` pins (mechanism 12).
